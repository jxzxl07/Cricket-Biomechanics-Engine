# CreaseLab model card

All figures below are generated by the scripts in `research/` and copied into the
runtime specs, so the API cannot claim more than was measured.

Two production models, both **trained in this repository on this project's own
clips**, both consuming the same pose features the API computes:

| | Batting | Bowling |
| --- | --- | --- |
| Spec | `batting_pose.json` | `bowling_pose.json` |
| Artifact | `batting_pose.onnx` | `bowling_pose.onnx` |
| Model | logistic regression over 12 pose features | random forest over 13 pose features |
| Classes | cut, drive, flick, pull, sweep, reverse sweep, scoop | left/right-arm pace, off spin, leg spin |
| Honest accuracy (leave-one-session-out) | **29.2%** | **56.5%** |
| On classes present in training | 42.4% (33/48 clips) | 72.2% (36/46 clips) |
| Random-split accuracy (leakage, reference only) | 66.7% | 75.7% |
| Abstain threshold | 0.60 | 0.40 |
| Displayed confidence cap | 0.60 | 0.75 |
| Training data | 48 clips, 7 classes, 3 sessions | 46 clips, 6 classes, 2 sessions |

Full reports: `data/evaluation/batting_pose_training_report.json`,
`data/evaluation/bowling_pose_training_report.json`. Dataset tables:
`data/evaluation/*_pose_dataset.csv`.

## Why these numbers are the honest ones

Every clip was recorded by one athlete in a handful of sessions minutes apart.
Clips from the same session are near-duplicates, so a random train/test split
puts almost identical footage on both sides and reports ~65–75%. That is the
number the earlier Random Forest baseline advertised (74.8% CV / 85.7% holdout);
it is leakage, not accuracy.

These models are therefore evaluated with **leave-one-recording-session-out**
cross-validation. The gap is printed in the spec on purpose: +37.5 points for
batting, +19.2 for bowling.

Two further limits are reported rather than hidden:

* Some classes exist in only one session (scoop and sweep were only recorded in
  the 09:30 session), so when that session is held out those classes are absent
  from training and cannot be predicted by any model. The raw figure includes
  them; the "classes present in training" figure excludes them. Both are shown.
* 48 and 46 clips are far too few for general shot recognition. These models are
  a measured baseline for this athlete and this camera setup.

## The broadcast video model is no longer used

`batting_video.onnx` (EfficientNetB0 + GRU, published by
[RITIK-12/CricketShotClassification](https://github.com/RITIK-12/CricketShotClassification),
MIT) was the earlier production classifier. It is kept for comparison and used
by `research/evaluation/batting_benchmark.py`, but the API does not load it.

Why it was retired, with measurements:

| | Value |
| --- | --- |
| Top-1 on this project's phone clips | 29.6% (chance 10%) |
| Top-2 | 52.3% |
| Macro F1 | 0.07 |
| Prediction spread | `straight_drive` × 37 of 44 clips |
| Mean confidence when wrong | 0.93 |

Two independent problems were found:

1. **Upstream preprocessing bug.** The graph starts with `Rescaling(1/255)` and
   ImageNet normalisation, so it expects 0–255 input; the published Streamlit
   demo feeds 0–1 frames. Correcting this raised our measured top-1 from 15.9%
   to 29.6% (`research/evaluation/batting_preprocessing_probe.py`).
2. **Domain mismatch.** Broadcast-trained pixel weights do not transfer to
   indoor phone footage. Pose-guided cropping, action-window sampling and flip
   averaging were all tested and did not help
   (`research/evaluation/batting_domain_probe.py`).

The pose models replaced it because pose features normalise away framing,
background and camera differences — the exact things that broke the video model
— and because they can be improved by adding data, while the frozen broadcast
weights cannot.

## Reproducing

```bash
python -m research.training.pose_dataset                 # labelled feature tables
python -m research.training.train_action_model --mode batting
python -m research.training.train_action_model --mode bowling
python -m research.training.publish_pose_model --mode batting
python -m research.training.publish_pose_model --mode bowling
```

Training requires `scikit-learn` and `skl2onnx` (see `requirements-research.txt`).
The API only needs `onnxruntime`; the preprocessing (median imputation, scaling)
is embedded in the ONNX graph, so serving cannot drift from what was benchmarked.

## Growing the dataset

The bottleneck is data, not the model. The pipeline ingests any dataset of clips
organised as `<class>/<clip>.mp4`, so a public corpus can be dropped in and the
same commands re-run:

```bash
python -m research.training.ingest_dataset --source /path/to/dataset --mode bowling
python -m research.training.pose_dataset --mode bowling
python -m research.training.train_action_model --mode bowling
```

ActionBowl (2,571 clips, 3- and 6-class bowling schemes) is the obvious bowling
corpus; it is distributed on Kaggle and needs Kaggle API credentials to fetch.
No redistributable weights for it were published, so the model has to be trained
here. See `research/training/ingest_dataset.py`.

## Pose model

`pose_landmarker_lite.task` is the MediaPipe Pose Landmarker Lite model
(33 landmarks with estimated depth, up to two poses). Pose-derived values are
approximate single-camera estimates: not laboratory motion capture, not medical
measurement, and not ball tracking.

## Safety scope

The product makes no bowling-legality judgement of any kind, does not diagnose
injury, and does not estimate ball speed. Estimated elbow angle at release is
reported as a neutral movement statistic. Coaching text is validated against a
list of banned claims before it is shown, and falls back to deterministic
metric-grounded feedback if it fails.
